# Glossary And Core Concepts KB

## What This File Governs

This file defines project-specific language. Use it to keep docs, code, UI copy,
and implementation discussions consistent.

## Tax Lien Intelligence Platform

A multi-tenant SaaS intended to turn tax lien and parcel datasets into structured
investment decision support.

Current status: auth, dataset upload, import readiness, focused manual mapping
repair, reusable import profiles, first-pass scoring, browser score review, watchlists,
portfolio/status tracking, and one county import adapter boundary are
implemented. Browser upload for single CSV imports is implemented. Broad county
coverage and automation remain future work.

## Multi-Tenant SaaS

A hosted application where multiple users or accounts share the system while
their data remains isolated. In this product, user-owned records must be scoped
by `userId`.

## Dataset

A user-uploaded county parcel or tax lien CSV file and its associated metadata.
Implemented as a tenant-owned dataset record with validation summary; normalized
source rows are stored internally for scoring, but public dataset responses
expose only metadata, validation summary, safe import summary context, and safe
readiness summary context.

## County Import Adapter

A deterministic upload-time mapping layer that can recognize a specific county
CSV shape from explicit headers and add canonical internal fields before
scoring. Current adapter: `maricopa_tax_lien_v1`. This is not broad county
coverage, live sync, scraping, or county identity verification.

## Import Summary

Browser-safe metadata on dataset responses that explains whether generic CSV
fallback or a county adapter handled the upload, which canonical fields were
mapped, the confidence level, and safe warnings. It must not expose raw source
rows.

## Import Readiness

Browser-safe metadata on dataset responses that explains whether recognized
fields are ready, partial, weak, or blocked for scoring review. It includes
field coverage, issue severity, guidance, and a scoring recommendation. It is
not a manual mapping editor, row correction workflow, or final underwriting
confidence score.

## Manual Mapping

Dataset-owned repair metadata that maps a supported canonical target field to a
source column from the uploaded CSV headers. Current manual mapping is limited
to parcel id, lien amount, estimated value, property type, and address. It does
not rewrite source rows or edit individual cells.

## Import Profile

Tenant-owned reusable mapping configuration saved from a scoring-ready dataset
repair. A profile stores supported target-to-source-column rules and normalized
header applicability metadata so future similar uploads can reuse the mapping
deterministically. It is not shared across users, generated by ML, or a full ETL
rule builder.

## Parcel

A property record derived from a dataset. It may later include identifiers,
location, value, lien amount, property type, and usability fields.
Not implemented yet.

## Score

A system-generated underwriting output for a parcel or lien. Current scores are
first-pass, rule-based outputs with investment, risk, liquidity, redemption,
confidence, flags, and reasoning. They are not final underwriting.

## Reasoning

Human-readable explanation for why a score exists. Reasoning is required for
trustworthy decision support and is included in current scored-record responses.

## Risk Flag

A warning generated by validation or scoring, such as missing data, poor value
coverage, unknown property type, or no road access.

## Watchlist

A user-owned shortlist of parcels or liens selected for further review.
Implemented as tenant-owned watchlist items that reference scored records.

## Portfolio

A user-owned record of actively tracked decisions or position candidates over
time. Implemented as tenant-owned portfolio items with a small status model and
score/reasoning snapshot.

## Ingestion

The process of accepting, parsing, validating, normalizing, and storing source
data.

## Enrichment

The process of adding safe derived context to source records before scoring.
Current enrichment is internal source-row inference from uploaded fields only.
External provider enrichment is future work.

## Enrichment Adapter

A backend extension point that derives safe enrichment output from a normalized
source row. Current adapter: `source_field_inference`.

## Scoring Package

The `packages/scoring` workspace package. Current implementation is a
pure, deterministic first-pass scoring engine. It should remain independent of
Express, MongoDB, and frontend presentation code.

## Source Of Truth

The authoritative place for product and implementation truth. For this repo, the
startup remote `oneclick` is the source-of-truth remote. The legacy personal
mirror is not product truth.

## Current Surface

What users can actually see or call today. Current callable API surface includes
health, auth, dataset, scoring, internal job detail, alerts, watchlist, and
portfolio endpoints. The browser surface includes login/register, dataset
list/detail review with import summary context, worker-backed scoring
trigger/status, scored table, record reasoning detail, alerts, watchlist review,
and portfolio tracking.

## Placeholder

A file or package that marks intended structure but does not yet implement the
real capability.

## Scaffold

Initial framework or package setup that enables future implementation.

## User-Owned Data

Data that belongs to one authenticated user or tenant and must be isolated from
all others.

## Tenancy

The ownership and isolation model for user data. In this product, tenancy centers
on authenticated identity and `userId`-scoped records.

## Drift

The gap between what docs, UI, specs, or prompts imply and what the repo actually
implements.

## Decision-Support System

A system that helps users evaluate options and make decisions, without claiming
to make final decisions or guarantee outcomes.

## Automation Layer

Future background or assisted workflows that reduce manual work while respecting
tenant isolation, validation, and explainability.

## Operator-Grade

A product feel that prioritizes clarity, reliability, data density, and repeated
workflow use over decorative or hype-driven presentation.

## Explainability

The requirement that important outputs, especially scores, include clear reasons,
warnings, and confidence context.

## Update Rules

Update this glossary when:

- new domain terms become part of product language;
- implemented meaning differs from earlier direction;
- UI copy or API names introduce new concepts.
